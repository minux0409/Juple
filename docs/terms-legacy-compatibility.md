# 기존 약관 동의 프로토콜 호환성

기준 HEAD: `7668bc51897810141c8c33676c7cd8a280deac8a`. 구현 완료 / 미커밋 / PROD 적용 대기.

## 복원 근거

2026-10-25 연령 정책 도입 직전의 공개 약관 소스에서 `2026-10-14` 문서를 복원했다. 원문을 새로 쓰거나 2026-10-25 본문에 이전 버전 이름을 붙이지 않았다.

- 원본 커밋: `e3445efb891551e7afbc8a6804520f7487546e15`
- `apps/web/lib/legalContent.ts` blob: `ee72f5da57a16002297ef6b6fe55c75131e46c8b`
- `apps/web/lib/legalConfig.ts` blob: `6eaad649f703622a1253fdf4e248fa4e46fde85a`
- 원본 함수와 그 시점의 공개 기본 설정을 실행해 만든 12개 절의 문서다. 당시 운영 환경에서 별도로 지정했을 수 있는 운영자 표시 값까지 소급 감사한 것은 아니다.
- 본문 SHA-256: `4559616eb6d94d7b9158e1e74f96cb33793394cc3d8b5889468a53c468b824c2`
- 기존 운영 호환 승인 기록: `docs/age14-rollout.md`. PROD 2026-10-14 및 기존 요청 형식을 유지하도록 기록돼 있다. 이는 모든 번역의 법률 검수 완료 증거는 아니다.

복원 자료는 `LegacyPublishedTerms.json`에 분리하고 원본 커밋·blob·해시를 보관했다. 기본 공개 `/terms`와 기본 문서는 2026-10-25를 유지한다. `?version=2026-10-14`는 그 원문만 표시하며, 현재 시행일 설정을 과거 문서에 임의 적용하지 않는다. 버전별 metadata도 해당 문서 기준이다. 승인되지 않은 멤버십 개정 초안은 등록하지 않았다.

## 요청 구분과 제한

1. contentHash와 language 필드가 **둘 다 존재하지 않을 때만** legacy 형식이다. 명시적 null, 빈 값, 일부 필드만 있는 요청, 잘못된 타입을 legacy로 낮추지 않는다. 알 수 없는 필드와 사용자 ID 입력도 거절한다.
2. legacy 예외는 복원한 2026-10-14 문서에만 연결한다. 실제 현재 정책도 2026-10-14여야 한다. 현재가 2026-10-25라면 2026-10-14 요청은 거절하며 현재 버전으로 자동 승격하지 않는다.
3. 해시·언어를 보낸 요청은 해당 버전 문서의 실제 해시와 허용 언어를 검증한다. 14/25 해시는 교환할 수 없다. 새 버전의 legacy 형식 요청도 거절한다.
4. 두 형식 모두 인증·소유자 조회 및 isAtLeast14=true가 필요하다. 해시·언어가 없다는 이유로 연령 확인을 생략하지 않는다.
5. 요청 형식은 설치된 앱 빌드의 증명이 아니다. 누구나 legacy 형식을 보낼 수 있으므로 예외는 기존 현재 버전에만 제한한다. 이는 기존 프로토콜 동의를 보존하는 것이며 구형 기기가 실제 어떤 문구를 읽었는지 새로 증명하는 기능은 아니다.

기존 요청 예:

```json
{"version":"2026-10-14","isAtLeast14":true}
```

신규 요청은 version·isAtLeast14·contentHash·language를 모두 사용한다. 해시는 문서 API에서 받은 실제 값을 써야 한다. 임시 해시나 임시 본문은 사용하지 않는다.

## 기존 기록 보존

- 이미 같은 버전을 동의한 legacy 재요청은 기존 상태를 그대로 돌려주며 저장하지 않는다. 원래 동의 시각이 유지된다.
- 2026-10-14 처리 시 이미 다른 버전이 기록되어 있으면 거절한다. 새로운 버전의 기존 기록을 과거 버전으로 덮어쓰지 않는다.
- 상태 조회 후 변경이 발생하는 경우도 고려해 저장소에서 읽은 User 자체에 같은 보존 검사를 적용한다. User의 기존 RowVersion/동시성 토큰은 유지했다. 저장 실패를 예외 무시나 기록 초기화로 처리하지 않는다.
- User 보존 동작은 단위 테스트했고 SQL 동시성 실행은 이번에 반복하지 않았다. 실제 SQL 경쟁 검증까지 새로 통과했다고 주장하지 않는다.
- 기존 데이터 보정, 동의 이력 재기록, DB 마이그레이션은 없다. 기존 스키마가 보관하는 버전·시각만 사용한다. 언어가 없던 과거 동의를 한국어 동의로 소급 표시하지 않으며 과거 언어/본문 열람 증거를 추정하지 않는다.

## 언어와 구독 보호

현재 복원한 공개 전문은 한국어다. 새 형식에서는 한국어만 동의를 허용하고 다른 16개 언어는 원문 열람과 기존 구독 관리만 허용한다. 기존 형식은 언어 미전달 상태로 기존 정책 동의를 처리하며 한국어로 간주하지 않는다. 과거 다국어 UI가 있었다는 이유로 번역 승인 상태를 바꾸지 않았다. 현대 클라이언트의 한국어 대체 동의 또는 번역 승인 정책은 미정이다.

미동의자의 기존 구매 조회·복원·스토어 관리 endpoint와 UI, 신규 구매/요금제 변경 제한, RTDN·갱신·취소·환불은 재개발하지 않았다. 관련 기존 관리 테스트만 회귀 확인하고 실제 결제나 기존 생명주기 테스트·DB 감사를 반복하지 않았다.

## 모바일 전환 계획

- Android 42 / iOS 11 기준 소스는 version·isAtLeast14를 보낸다. 이 형식은 현재 정책 2026-10-14에서 복원한 원문에 한정해 성공한다. 실제 바이너리 재설치·실기기 확인은 이번에 하지 않았다.
- Android 최소 24 / iOS 최소 1은 유지했다. 연령 값을 보내지 않는 더 오래된 앱은 400이다. 해당 앱까지 새 동의를 가능하게 만들려면 새 클라이언트가 필요하며 서버에서 연령 확인을 대신 채우지 않는다. 최소 정책을 유지했다는 것이 모든 과거 바이너리의 신규 동의를 보장한다는 뜻은 아니다.
- 이번 코드만으로 기존 바이너리에 미동의 전용 구매 관리 UI가 생기는 것은 아니다. 스토어 자체의 구독 관리·취소는 별도로 이용 가능하다.
- 호환 API 배포를 별도 승인받아 준비한 뒤 신규 Native를 공개 배포한다. 설치 가능성·서명·데이터 유지 업데이트 확인 후 그 실제 빌드를 최소 지원 후보로 정한다. 새 빌드 번호는 확정하지 않는다.
- 새로운 약관 버전은 원문·언어·고지·동의 승인 이후에만 선택한다. legacy 예외를 새 버전에 확대하지 않는다. 강제 동의 및 멤버십 활성화는 별도 승인이다.

- Backend 관련 단위 테스트 47개 통과: legacy/modern 성공, 버전·해시·언어 불일치, null/부분/잘못된 타입, 연령 누락·false, 다른 버전 덮어쓰기 방지, 동의 시각 보존, 인증 속성 및 기존 구매 관리.
- Mobile 관련 Jest 35개 통과: 기존 동의 흐름과 구독 관리, 서버의 2026-10-14 문서 파싱·버전 격리. Mobile TypeScript 통과.
- Web 관련 테스트 60개 통과: 원본 해시·provenance, 생성본 일치, 과거 문서 선택, 기본 공개 버전 불변, 기존 동의·구독 관리 정책. Web TypeScript 및 변경 파일 ESLint 통과.
- Backend 빌드 통과. 기존 인증서 로딩 API 및 테스트 경고는 변경하지 않았다. 전체 결제·체험·SQL Integration과 전체 Web/Mobile 테스트는 반복하지 않았다.

## 운영 적용 전 남은 조건

한국어 및 legacy 프로토콜의 2026-10-14 문서 누락·요청 형식 차단은 코드에서 해결했다. 비한국어 현대 동의 허용 정책, 연령 값 없는 구형 앱의 전환, 실제 단말 호환 검증은 여전히 별도 결정/확인이 필요하다. 원문 복원은 멤버십 개정안의 승인이나 720시간 정책의 법적 시행 승인이 아니다.

ProgramEnabled=false, PROD 약관 버전·시행일·강제 동의 및 지원 앱 정책을 변경하지 않았다. PROD 배포, 실제 동의 저장/체험 지급, Commit/Push는 하지 않았다. 보호 파일 3개와 기존 미추적 감사 문서는 보존한다.
